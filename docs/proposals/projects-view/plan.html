Jak pracuję

  1. Makiety każdej funkcji w 2–3 wariantach (osobna strona) → wybierasz → dopiero wtedy kod tej funkcji.
  2. Kod etapami, na gałęzi claude/clouding-project-management-view-uu34tq. Każdy etap: npm test + npm run check zielone, screenshot z prawdziwego okna (na danych testowych) położony obok zatwierdzonej makiety.

DANEelectron/lib/clickupClient.js · electron/clickupCache.js

0.2ClickUp — klient tylko do odczytu

  • Token z Keychaina tą samą komendą co w wiki (security find-generic-password -a clickup-api -s clickup-api-token -w), nagłówek z surowym tokenem, nigdy nie zapisywany na dysk ani do logów. Brak tokena → czytelny komunikat w widoku, nie błąd.
  • Wyłącznie GET: zadania listy z paginacją i zamkniętymi (/list/<id>/task?include_closed=true&subtasks=true&page=N), statusy listy, jeden task, komentarze, a w ustawieniach przeglądanie spaces → folders → lists.
  • Z taska bierzemy: id, custom id, nazwę, status + jego kolor, przypisanych, due date, date_closed/date_done, custom fields (w tym Spec URL), linki do innych tasków, URL.
  • Cache na dysku per lista → widok otwiera się od razu, także offline, z napisem „refreshed 12 min ago”. Odświeżanie: przy wejściu w projekt, co 5 min gdy widok jest otwarty, ręcznie ↻. Limit ClickUpa (100 zapytań/min) pilnowany kolejką.
  • Testy: paginacja, mapowanie pól na zapisanych odpowiedziach API, zachowanie bez tokena, błąd sieci → zostaje cache.

Domyślna mapa według kolejności z Walktober Web (pending review → Open → in progress → feedback → issues found → in staging → ready for prod → … → Closed); nieznany status dopasowany po nazwie, a jeśli się nie da — widoczny jako „other” zamiast cichego zgadywania.

DANEelectron/lib/gitInspector.js

0.4Git — gałęzie i staging, lokalnie

  • W każdym skonfigurowanym repo (blueprint, prime) szukamy gałęzi CU-<task id> (też z sufiksami typu -1, -WAL) lokalnie i na origin, oraz worktree'ów (git worktree list --porcelain).
  • Dla gałęzi: ile commitów przed origin/docker-deploy, czy jest już w origin/docker-staging (merge-base --is-ancestor), czy jest wypchnięta, czy worktree ma niezacommitowane zmiany.
  • Tylko komendy czytające; git fetch nie odpala się sam (decyzja nr 4 niżej).
  • Testy na tymczasowym repo tworzonym w teście (gałęzie, worktree, merge do stagingu).
DANEelectron/lib/pullRequests.js

0.5GitHub — PR-y i CI

  • Przez gh pr list --repo hesdevs/<repo> --state all --json number,headRefName,baseRefName,state,url,statusCheckRollup — jedno zapytanie na repo, dopasowanie po nazwie gałęzi. Wynik: numer, stan (open / merged / closed), dokąd (staging / deploy), CI zielone / czerwone / w toku.
  • Gdy gh nie jest zalogowane → na kartach „PR: gh not signed in”, reszta działa. Logowanie robisz Ty.

0.6Łączenie sesji z taskami

  • Kolejność reguł, pierwsza wygrywa: ręczne powiązanie → gałąź sesji (gitBranch, które Claude Code już zapisuje) albo folder roboczy zawierający CU-<id> → pierwszy prompt / tytuł z linkiem app.clickup.com/t/<id> albo CU-<id> → transkrypt (skan pierwszych wiadomości, zapamiętany po dacie pliku, żeby nie czytać w kółko).

DANEelectron/lib/pipelineStage.js

0.7Gdzie jest task w Twoim pipelinie

  • Spec: no spec → session (jest sesja Spec Writera) → draft → review / approval → approved. Z etapu na liście speców + obecności sesji.
  • Build: open → builder (jest sesja buildera) → branch → PR → staging (gałąź w docker-staging) → QA (status „in staging” / „issues found”) → prod.
  • Łączenie taska buildowego ze spekiem (ustalone z notatek Buildera): task z listy Initial Build Web ma zależność „depends on” na planning task, a planning task ma pole Spec URL → strona speca w doku Product v2 173fz-212393. Czyli: dependencies z API → planning task → Spec URL. Gdy łańcuch się urywa — ręczne powiązanie.
  • „Czeka na mnie”: needs answer w sesji, status feedback przypisany do Ciebie, review speca, niewypchnięta gałąź z gotowym builderem, czerwone CI.
  • Testy tabelaryczne: każda kombinacja statusu / gałęzi / PR-a → oczekiwany etap.

  • Liczby w kubełkach, per osoba (Ty / każdy przypisany / nikt), ile speców do napisania i w review, ile PR-ów z czerwonym CI.
  • „Left to close”, tempo z ostatnich 2 tygodni (z date_closed), tempo potrzebne do ostatniego deadline'u; historia do burn-downu odtwarzana z dat zamknięcia.
  • Oś czasu: procent upływu czasu między startem a ostatnim deadlinem, najbliższy deadline, dni do niego.
